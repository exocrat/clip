# Campus Marketplace — Stubs and Real Integration Gates

**Canonical path:** `docs/architecture/stubs-and-integration-gates.md`

## Rule and meaning

After **real PRE-00 and DL-00**, independent domain work can start against reviewed deterministic test doubles even when an upstream implementation is not ready. A stub supplies synthetic responses through the frozen public interface; it does not implement the upstream service or prove integrated behavior. The domain task list remains the sole numbered feature procedure. This document specifies allowed execution checkpoints and the real gates that cannot be substituted.

Prerequisites for *isolated work* differ from prerequisites for *real integration and acceptance*. Completion arrows in the dependency graph retain real gates; dashed early-start arrows show the permitted parallel implementation route. Do not delete a required gate just because a stub allows work to start.

## Staged execution without silent omissions

1. At task start, check each dependency against the work log, accepted revisions, task evidence, and active owner branches/PRs. Read the real PRE-00/DL-00 evidence and exact upstream contract/source version before choosing the mode. Inspect active owners/PRs before making a second adapter. If a contract or requirement/security decision is absent, inconsistent or unclear, ask; a stub cannot resolve that uncertainty.
2. In the task understanding report name the execution mode (`isolated with test doubles` or `real integration`), eligible steps from the table below, missing real dependencies, allowed adapter/scenarios, checks and pending obligations. Human verification of that concrete scope is required before edits. Routine implementation of a documented stub does not require inventing a new product decision.
3. At the first eligible domain step create/reuse its owned adapter/fixtures and register exact test commands. Use the existing public types/generation source; never fork an incompatible production API. Bind trusted fake identities only through an explicit test dependency override, never a client-supplied user ID or public auth bypass.
4. Execute numbered steps in their existing order, one verified increment at a time. Where the table permits staging, finish the **isolated** portion, record each real subaction/check as pending with its original task/step ID, and ask the human to verify the isolated result and authorize the next checkpoint. The step state remains `partial: isolated verified; real integration pending`, not performed/accepted. This explicit exception permits the next eligible numbered step; it does not allow arbitrary skipped requirements or silent reordering.
5. Keep an append-only pending-integration entry in `docs/status/work-log.md`: task/step, contract version, fake paths/scenarios, real dependency/accepted revision needed, owning human, trigger, exact checks/expected result and current evidence mode. Distinguish code/test progress from accepted milestone/full completion. A fake response is never evidence that another task or resource exists.
6. When the real prerequisite becomes available, refresh accepted main/contracts, stop before the next new isolated increment and report the earliest pending integration checkpoint. Obtain human understanding verification, connect the real adapter/schema/provider, reconcile migrations/data and run the original real checks. Integrate through owner-reviewed PRs; preserve human verification for each returned checkpoint. A real implementation defect is not hidden by continuing to use the fake.
7. Accept readiness/full completion only when every required real dependency/check for that gate passes, evidence is tied to the real revision, the human verifies and peer-reviewed merge requirements hold. Keep any remaining deferred check pending; no final FR/NFR/task acceptance from fake-only results.

## Test-double quality and isolation

- Freeze success plus denied/expired/missing/malformed/unavailable/duplicate/retry/timeout cases from the public contract. Fail tests when the consumer accepts an unexpected schema/error; a constant always-success response is insufficient.
- Public interface signatures/types/errors must match real adapters. Use generated sources where applicable. Owners review assumptions; a contract change regenerates/retests affected doubles and consumers.
- Keep deterministic synthetic users, listing IDs, contacts and provider responses. Never use real private data, credential values, message keys or plausible live recipient accounts.
- Test overrides live in owned fixtures/test-only dependency bindings, not default production paths. CI covers fake-activation rejection and real-adapter selection; deployed startup fails closed if a fake/incomplete security-critical dependency is selected. Never expose a public test-auth route or silently fallback from a real dependency to a fake.
- Local browser demos may use an explicitly labeled isolated test mode on loopback with synthetic data. They are not cloud acceptance/NFR evidence and cannot enter the shared deployed runtime.
- Validate integration parity with both the same boundary scenarios and real-state behavior: actual auth/ownership, schema integrity, listing changes/search sync, participants/key binding, unread state/recipient choices, storage policy and provider side effects.

## Exact non-substitutable evidence

Real sign-in/account expiry/revocation, integrated authorization/ownership/participant checks, foreign-key/migration integrity, actual contact consent/disclosure, actual encryption/key binding, listing-to-search update propagation, cloud S3/IAM behavior, durable producer/read-before-due notification behavior and live provider delivery all need their real relevant path. Local fixtures can test consumer failure handling but cannot prove those integrations. Every NFR uses its canonical accurate procedure; NFR-04 is offline on final real ranking/data, while cloud latency/capacity/recovery/restore claims need actual deployed resources/revisions.

This is a bounded parallel-development mechanism, not a general permission to bypass every dependency. If the table does not authorize the proposed staging, the agent reports the blocked checkpoint and asks about a concrete scoped change rather than guessing.
