# CN-01 Step 2 — E2EE security design proposal

**Status:** User-approved direction; runtime adoption is pending team source/dependency review and implementation checks. The selected candidate is `@open-e2ee/signal-protocol-sdk@13.0.0`; the user approved the v1 application message payload and one-device public-prekey relay contract. The package has not been added to the repository manifest or lockfile in this step.

**Origin:** CN-01 Step 2.
**Prepared:** 2026-10-20.

## Requirements and boundary

- Message text and private conversation payload are encrypted and decrypted only in participant clients. The service stores and relays ciphertext, public-key metadata, and the routing/timing metadata already specified in the [Conversations contract](../../contracts/conversations.md). OpenE2EE retry requests are the explicit exception: they are unencrypted protocol-control metadata, not chat content, and are stored/routed only between the two authorized participants.
- MVP supports one active browser device/key bundle per account. Private keys are not server recoverable; losing browser key state can make retained history unreadable.
- The authenticated account must be bound to its own public-key registration. Message envelopes must bind the conversation, payload kind, sender, recipient, and referenced key versions. The server must reject a sender/recipient/key-version mismatch without learning the plaintext.
- Required evidence includes a two-client exchange and rejection of tampering, wrong-key/wrong-recipient use, unauthorized reads, key changes, and key loss. No ciphertext, plaintext, key material, or contact values may enter logs, traces, analytics, screenshots, or evidence.
- The service necessarily sees participant and conversation identifiers, entry kind, sequence, key-version references, ciphertext size, timing, and read-watermark state. This metadata is not hidden by E2EE.

## Browser/library candidates for evaluation

OpenE2EE is the selected candidate, subject to team review of this exact source and complete production dependency tree before runtime adoption. As checked on 2026-10-22, npm lists `13.0.0` as latest, its package license is `(MIT OR Apache-2.0)`, and its declared Node engine (`>=22.12.0`) is compatible with the repository's Node 24.x/npm 11.x requirement. The other rows remain evaluated alternatives, not selected paths:

| Candidate | Fit and advantages | Material caveats to resolve |
|---|---|---|
| OpenE2EE Signal Protocol SDK (`@open-e2ee/signal-protocol-sdk`) | Its project documentation describes a browser-capable TypeScript Signal-Protocol-derived implementation, device-local protocol state, and an application-provided transport/relay. This fits CLIP's existing ciphertext API without adopting a new messaging server. The selected release is `13.0.0`. | **Team-review gate:** before runtime adoption, the team reviews the exact source, complete production dependency tree, license/provenance, protocol profile, persistence adapter, and security model. Record the reviewed revision and conclusion; stop and revisit if a security question cannot be resolved. No independent/external reviewer is required. It is not affiliated or wire-compatible with Signal/libsignal. Browser persistence is same-origin state, not protection against hostile same-origin JavaScript/XSS. The user accepts the SDK's default PQXDH/ratcheting behavior if it needs no dedicated post-quantum infrastructure or manual crypto setup; ordinary browser/IndexedDB, secure-context/CSP and CLIP relay integration remain required. |
| Per-message authenticated HPKE (RFC 9180 Auth mode; no ratchet) | A smaller design candidate for 1:1 messaging: use a maintained browser-capable HPKE implementation for each message. It may satisfy the PRD's server-cannot-read-content requirement if the team explicitly accepts the weaker compromise guarantees and permits the application-level envelope/session work. | **CN-01 scope decision required:** HPKE is a standard encryption scheme, but CLIP still must define context, sender-history access, replay/deduplication, ordering and retry behavior around it. If that app-specific protocol work is considered outside the approved scope, rule HPKE out rather than quietly composing a custom chat protocol. HPKE Auth is recipient-only: the sender cannot decrypt their own message from the recipient ciphertext. Re-reading sent history would require a second ciphertext addressed to the sender's own public key or a locally persisted plaintext copy; neither is chosen. RFC 9180 also identifies key-compromise impersonation: compromise of the recipient private key can let an attacker forge messages that the recipient accepts as coming from any sender. If that property is unacceptable, HPKE Auth alone is ineligible; any signature mitigation over the encapsulated key/ciphertext would require its own reviewed identity-binding and envelope design. Recipient-key compromise can expose retained ciphertext; HPKE alone does not prevent replay or tolerate message loss/reordering. A browser-capable JavaScript implementation found in this review supports RFC 9180 modes but says it has not been formally audited. It is therefore not a “well-audited” drop-in and remains eligible only after explicit scope approval, security review, and acceptance of all these properties. |
| Matrix Rust crypto WASM / `matrix-js-sdk` | Maintained Rust-backed E2EE exposed to JavaScript/WebAssembly and explicitly usable by browser clients. It provides an established protocol implementation rather than asking CLIP to compose primitives. | Matrix crypto is not only a cipher package: normal operation assumes Matrix devices, rooms, room events, device/key discovery, and to-device key-sharing flows. Its state machine may rely on those semantics. Adapting it to CLIP's custom REST/envelope contract would require substantial protocol/storage/transport glue and testing; using the SDK normally implies a Matrix-compatible server and a broader architecture change. Treat this as an architecture decision and do not add Matrix infrastructure or change the approved architecture under CN-01 without separate approval. |

The official Signal `libsignal` repository is relevant as a protocol implementation/reference, but its published npm build targets native Node platforms and does not currently document a supported browser package; it is not treated here as a drop-in browser candidate. The browser Web Crypto API is broadly available only in secure contexts, but it exposes low-level primitives, not a complete authenticated messaging protocol. Composing those primitives into a new protocol is outside scope and prohibited by CN-01.

## Common design questions before implementation

1. **Account and key authentication (selected direction):** Trust keys supplied by CLIP's authenticated account directory; no safety-code/fingerprint verification is planned for MVP. This does not protect against a malicious or compromised directory substituting a peer key, and a first-contact key is not independent proof of the intended human's identity. Register/replace only the authenticated account's own bundle through the reviewed API. Bind every message operation to authenticated membership and server-validated sender/recipient key versions. A changed peer key blocks sending; under this trust model, unblock only after the user sees and deliberately accepts the newly directory-provided key, with a clear explanation of the trust limitation. A server signature/HTTPS connection alone does not prove the server-supplied peer key is the intended human's key if the server itself is malicious.
2. **Browser state and device constraint (selected direction):** The product decision is no key backup or recovery. The user accepts that clearing browser data, losing the device, private-browsing exit, or browser eviction can remove usable key state and make affected retained history permanently unreadable. Use OpenE2EE's `indexedDbStore` for browser-local protocol state and IndexedDB for the local decrypted chat-history cache; do not send that cache to CLIP's server. Browser storage is best-effort by default and eviction/quotas vary; requesting persistent origin storage may reduce automatic eviction but cannot prevent a user clearing data or guarantee access on every browser. IndexedDB is available to same-origin scripts; the SDK documentation notes same-origin code can access its stored records and key. Require a secure context, restrictive CSP, XSS-safe rendering, no plaintext in logs/analytics/evidence, and a warning plus acknowledgement before key registration. No password wrapping, export, backup, or recovery mechanism is planned.
3. **Key change, peer experience, unblock action, and history:** Enforce one active bundle per user while preserving public versions referenced by retained envelopes. A changed/unrecognized peer key blocks sending and shows “key changed—verify this person”; there is no ignore/continue-through-warning path. Define an explicit unblock action alongside the trust model: under account-directory-only trust, the user must deliberately acknowledge and accept the newly registered key after seeing that this trusts the account directory and does not prove the same human controls it; under safety-code/fingerprint trust, the participants compare and confirm the new code through the approved independent channel before sending resumes. Both paths must log no secret values and preserve a visible key state. If the peer lost their key, the new key does not restore old history. Decide whether old retained messages remain readable only where old private state remains available; never claim a new key can recover old history. Require product sign-off on the registration warning and permanent-history-loss consequence.
4. **Authenticated context and routing (selected direction):** Keep SDK-produced ciphertext opaque; do not add another encryption layer or re-encode protocol ciphertext. Public key bundles use typed JSON fields that mirror the SDK's `PreKeyBundle` data shape; the browser adapter decodes canonical Base64 public-key bytes and assembles the SDK object. Validate exact key and signature lengths at the API boundary, while leaving cryptographic signature verification to the SDK. The outer `CipherEnvelope` carries `sdk_message_type`, `client_timestamp_ms`, key-version references for encrypted messages, and opaque SDK payload bytes. The client timestamp matches the SDK envelope timestamp and is SDK replay/retry metadata only; server sequence and activity timestamps remain authoritative. The v1 application payload carries the authenticated conversation, kind, sender, recipient, key-version context alongside content. After successful decryption, the recipient compares that context with the outer fields and rejects any mismatch. The API server can reject mismatched *claimed outer metadata* against its membership/key records, but that is not cryptographic proof that the ciphertext binds those values. The recipient performs that cryptographic/context verification. `operation_id` is reused as SDK `clientMessageId`. Exact SDK API behavior remains a team implementation check.
5. **Metadata and failures:** Preserve only contract-approved routing/timing fields and ciphertext on the server. The SDK's unencrypted retry-control payload may contain failure reason, a failed-message timestamp, and ratchet/retry identifiers; CLIP does not inspect or log it and only routes it to the other authorized member. A cryptographic/storage/key-state failure must stop the send or display operation without plaintext fallback; retry must not reuse one-time protocol state unsafely. The browser's local decrypted-history cache is intentional and remains on-device. Keep server errors, notifications, logs, analytics, and evidence content-free.
6. **Ordering, retries, and replay (accepted direction):** The user accepts this product behavior independently of library capabilities. API sequence is authoritative; clients render in ascending sequence, deduplicate retries by the reviewed entry/operation identity, detect a missing sequence and recover it through incremental retrieval, and acknowledge only messages actually displayed. Test duplicate submission, replayed ciphertext, delayed/reordered delivery, temporary disconnect/reconnect, sequence gaps, and an unrecoverable missing message without falsely acknowledging it. Bound any ratchet skipped-message work if the selected protocol has that concept. A design that cannot meet those tests is not eligible just because its library labels the operation supported.
7. **Browser-origin and dependency policy:** No remotely hosted third-party script, analytics/session-replay tag, or third-party runtime injection may execute on the conversation origin. Every bundled runtime dependency (including UI, telemetry and transitive packages) must be allowlisted, pinned via the lockfile, checked for provenance/license/advisories, and reviewed before updates; no dependency is exempt because it is “only UI.” Use a strict CSP with no broad script sources or unsafe eval, safe rendering, and no third-party iframe on the conversation page. These controls reduce exposure but do not make same-origin code unable to access/invoke client keys. Record this as a concrete web-security gate, not as a claim that CSP prevents all XSS.
8. **Team source and dependency review/go-no-go:** Before runtime adoption of `13.0.0`, the team reviews the exact source revision, complete production dependency tree, license/provenance, protocol profile, key/storage/trust design, and adversarial test plan, and records its conclusion. This is a team review; an independent or external reviewer is not required. If the team cannot resolve a security question, stop and revisit the candidate. The package release and v1 application payload format have been selected; this contract work does not claim the source/dependency review or runtime security tests are complete.
9. **Verification plan:** After team source/dependency review, pin the selected package release and reviewed dependency tree in the lockfile. Add deterministic two-client tests for initial exchange, both directions, restart persistence, replay/duplicate/out-of-order behavior, altered ciphertext/context, wrong peer/key, key replacement/re-verification, lost/evicted local state, and server-side ciphertext-only storage/logging. Use synthetic test identities/keys only. Test browser persistence/clearing, registration-time warning, peer key-change UI, dependency/CSP policy, and failure UI; no cloud measurement in this step.

## Remaining review and implementation checks

The user has approved the direction and format choices below. The remaining work is team source/dependency review and implementation verification, not another product-choice vote.

1. **Review the selected OpenE2EE release.** Review `@open-e2ee/signal-protocol-sdk@13.0.0`, including exact source and full production dependency tree, license/provenance, protocol profile, persistence/trust design, and adversarial test plan; record the team's conclusion. No external/independent review is required. Do not integrate runtime behavior if material security questions remain unresolved.
2. **Confirm the security-property scope and candidate fit.** Forward secrecy/ratcheting is not a CLIP requirement, but the user accepts OpenE2EE's default PQXDH/ratcheting behavior if it needs no dedicated post-quantum service or manual crypto setup. Official browser guidance indicates the PQ operations are SDK defaults, not a separately provisioned service; standard browser integration still needs the SDK and IndexedDB helper dependency, secure context/CSP, and CLIP's auth/relay adapter. Do not disable library protections. The team must verify this against the exact reviewed release and confirm the concrete API meets authenticated-context and ordering/retry requirements. HPKE and Matrix are not the chosen path.
3. **Key trust and rotation:** Account-directory trust is selected; no safety-code/fingerprint requirement for MVP. Sending stays blocked on a changed key until the user deliberately accepts the new directory-provided key after seeing the trust limitation.
4. **Browser persistence and loss UX:** Use the SDK's IndexedDB adapter and a local decrypted-history cache. No backup or recovery will be provided, and permanent history loss after browser key-state loss is accepted. The registration-time warning/acknowledgement is required in the UI implementation.

The user accepts the no-third-party-runtime-script, CSP, safe-rendering, bundled-dependency review, and ordering/retry/replay policies described above. The v1 application payload carries authenticated context inside the encrypted content for recipient-side comparison with server routing fields. The server's check only validates claimed outer metadata; cryptographic context verification is performed by the recipient after decryption. The exact SDK integration and adversarial tests remain implementation checks.

The intended architecture keeps cryptography/key management behind a narrow client-side boundary, separate from conversation UI/domain behavior and the server API's ciphertext envelope. This makes a future product-approved change in encryption policy easier to isolate, without a plaintext fallback or dual-mode bypass. The selected package and v1 app-payload direction are recorded; the repository production dependency pin, SDK integration, and key/message runtime implementation remain pending team review and their later CN-01 steps.

## Sources checked on 2026-10-22

The tagged SDK source review confirmed that relay reconstruction requires a
message type and client timestamp in addition to ciphertext bytes. The CLIP
contract therefore carries those as explicit transport metadata, maps its
stable `operation_id` to `clientMessageId`, and keeps SDK timestamps separate
from authoritative server ordering/activity timestamps. The SDK's
`retry_request` is unencrypted; CLIP models it as an ordered, non-rendered
protocol-control entry with no unread-text or notification side effects. Its
exact two-client runtime handling remains to be tested in CN-01.
