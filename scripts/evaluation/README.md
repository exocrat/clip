## NFR-05 — Active chat

`nfr05_browser.mjs` captures actual sender-submit and recipient-display events

# NFR-05 offline outcome preview

`nfr05_report.py` reads a local JSON object containing only `samples`: up to 60
records with unique integer `index` values 0–59, `outcome` (`displayed`,
`failed`, or `undisplayed`), `submitted_ns`, and `displayed_ns`. Times are
nonnegative integer nanoseconds from the same host monotonic clock; displayed
records require both times, other outcomes require `displayed_ns: null`, and a
failure before submission may also use `submitted_ns: null`. Do not include
message content, ciphertext, account identifiers or credentials. For example:

```json
{"samples":[{"index":0,"outcome":"displayed","submitted_ns":0,"displayed_ns":5000000000}]}
```

This incomplete example is refused as a passing preview because 59 outcomes are
missing. Run `python -m scripts.evaluation.nfr05_report observations.json` to
print aggregate counts. At least 57 of all 60 must be displayed within five
seconds, and all outcomes must be present. `threshold_met_if_valid` is only
arithmetic; clock, browser-display events, background load, privacy and all
other NFR-05 gates still need real evidence and review. The tool cannot run a
workload or assert an NFR pass.

`nfr05_events.collect` is an in-memory adapter for simulated events with only
`index`, `event` and `time_ns`. It accepts a submission followed by an explicit
displayed, failed or undisplayed outcome; a failure may occur before submission.
An undisplayed outcome cannot be recorded before the five-second deadline and
is final, so the eventual real observer must wait until its observation window
ends before emitting it. A submission without a final outcome remains missing.
Server receipt is not display. The adapter checks ordering and rejects extra
fields, but does not observe a browser or verify events or timestamps.

`nfr05_browser.mjs` captures sender-submit and recipient-display events through
two loopback Chrome DevTools connections, then starts the hash-bound comparison
profile as a 10-read/s browse/search/detail mix for the 300-second message
window. It stores no message text, keys, cookies or ciphertext. The raw k6 JSONL
is separate and private; background validity requires 3,000 correctly
accounted responses and zero drops. A capture still requires human review and
does not accept NFR-05.

## NFR-06/07/08 recovery and spend preparation

`nfr06_recovery.py` binds an ECS task, service, target group, account and region
to a reviewed plan. It checks two healthy serving tasks, runs the 60-second
one-read/s baseline, and will call `ecs.stop_task` only when a second, unexpired
approval names the exact task and run. It then continues the one-read/s stream
while checking restored ECS and ALB capacity against the 240-second limit.
Cookies stay in `CLIP_NFR06_SESSION_COOKIE`; output is private and excludes
response bodies. The script does not deploy or create infrastructure.

`nfr07_restore_observer.py` checks that the approved snapshot is the latest
available automated backup for the named source, refuses an existing target,
and restores only to a new private RDS instance matching the approved subnet and
security groups. A separately approved action file binds snapshot, target,
instance class and network. It times through read-only SQL checks for the
migration head, validated foreign keys and representative user/listing/wanted/
conversation/offer relationships. It also verifies a declared ECS smoke
service's image digest and database URL parameter, confirms the parameter points
to the restored RDS endpoint, checks healthy ALB targets, then performs an
authenticated `/api/me` and wanted-request detail read. The service and its
parameter must already exist under a separately reviewed plan. The tool leaves
NFR acceptance to human review and never deletes the restore target.

`nfr_cost_ledger.py` validates a project ledger of billing evidence, delayed
charges and retained-resource estimates. It keeps AWS credits separate from
gross project spend, rejects duplicate source lines and overlapping periods,
and avoids counting a forecast again after an exact billing entry replaces it.
It shows headroom against USD 200 and tracks credits separately; the earlier
USD 10 credit-use cap does not apply to this experiment.
It makes no cloud calls and cannot accept NFR-08; final scope and human review
remain required.

`k6/exp05_pilot.py plan` creates the EXP-05 ECS baseline and four required
Lambda/ECS weight candidates (100/0, 75/25, 50/50 and 25/75), with three
repetitions each and the same 50-request/s burst profile. `report` checks all 15
run summaries for complete delivery/accounting, the 95% correct-operation
floor, zero generator drops, routing evidence, telemetry, database/generator
headroom and the approved cost cap. It can recommend the highest Lambda share
that passes those frozen gates, but leaves selection for human review and never
freezes the main experiment weight. The plan remains draft and does not launch
traffic or authorize deployment.
